# MySQL 性能优化实战指南

性能优化是 DBA 的核心竞争力之一。本文从索引优化、慢查询分析、参数调优三个维度，系统梳理 MySQL 性能优化的方法论与实战技巧。

## 一、索引优化 (Index Optimization)

索引是提升查询性能最有效的手段，但错误的索引设计反而会拖慢写入速度。

### 1. 索引底层原理 (B+ Tree)
*   **聚簇索引 (Clustered Index)**：叶子节点存储完整的行数据。主键就是聚簇索引。
*   **二级索引 (Secondary Index)**：叶子节点存储索引列值 + 主键值。回表查询时，先查二级索引拿到主键，再回聚簇索引查完整数据。

### 2. 核心优化策略
#### (1) 最左前缀法则 (Leftmost Prefix Rule)
对于联合索引 `(a, b, c)`：
*   **生效**：`WHERE a=1` / `WHERE a=1 AND b=2` / `WHERE a=1 AND b=2 AND c=3`
*   **部分生效**：`WHERE a=1 AND c=3` (只用到 a，c 无法走索引)
*   **失效**：`WHERE b=2` / `WHERE c=3` (跳过首列)

#### (2) 覆盖索引 (Covering Index)
查询的字段正好都在索引中，无需回表。
*   **优化前**：`SELECT * FROM user WHERE age=20;` (若 age 是索引，需回表查 name 等字段)
*   **优化后**：`SELECT id, age FROM user WHERE age=20;` (直接从 age 索引树返回数据)

#### (3) 避免索引失效
*   **函数计算**：`WHERE YEAR(create_time) = 2023` ❌ -> `WHERE create_time BETWEEN '2023-01-01' AND '2023-12-31'` ✅
*   **类型转换**：字符串字段不加引号会导致隐式转换。`WHERE phone = 13800000000` ❌ -> `WHERE phone = '13800000000'` ✅
*   **模糊查询**：`LIKE '%abc'` (前缀模糊) 会失效；`LIKE 'abc%'` (后缀模糊) 走范围索引。
*   **OR 条件**：若 `OR` 连接的列中有一个没有索引，则所有索引失效（除非使用 Index Merge）。

### 3. 使用 EXPLAIN 分析执行计划
```sql
EXPLAIN SELECT * FROM user WHERE id = 1;
```
**关键字段解读**：
*   **type** (访问类型)：性能从高到低：`system > const > eq_ref > ref > range > index > ALL` (全表扫描)。
    *   **目标**：至少达到 `range` 级别，最好是 `ref`。
*   **key**：实际使用的索引。
*   **rows**：预计扫描行数 (越少越好)。
*   **Extra**：
    *   `Using index`：使用了覆盖索引 (好)。
    *   `Using where`：需回表过滤。
    *   `Using filesort`：无法利用索引排序，需文件排序 (差，需优化)。
    *   `Using temporary`：使用了临时表 (极差，需优化)。

## 二、慢查询分析 (Slow Query Analysis)

### 1. 开启慢查询日志
在 `my.cnf` 中配置：
```ini
[mysqld]
slow_query_log = 1
slow_query_log_file = /var/lib/mysql/slow.log
long_query_time = 1  # 超过1秒记录
log_queries_not_using_indexes = 0 # 是否记录未使用索引的SQL
```

### 2. 分析工具
#### (1) mysqldumpslow (原生)
```bash
# 访问次数最多的10条SQL
mysqldumpslow -s c -t 10 /var/lib/mysql/slow.log
# 耗时最长的10条SQL
mysqldumpslow -s t -t 10 /var/lib/mysql/slow.log
```

#### (2) pt-query-digest (推荐)
Percona Toolkit 工具，生成的报告更详细。
```bash
pt-query-digest /var/lib/mysql/slow.log > slow_report.txt
```
**报告关注点**：
*   **Query ID**：SQL 指纹。
*   **Response time**：总耗时占比。
*   **Rows examine**：扫描行数 vs 返回行数 (Rows sent)。如果扫描 100万行只返回 10 行，说明索引极差。

### 3. 优化流程
1.  抓取 Top 10 慢 SQL。
2.  `EXPLAIN` 分析执行计划。
3.  判断是索引缺失、索引失效还是写法问题。
4.  优化索引或重写 SQL。
5.  验证效果。

## 三、参数调优 (Configuration Tuning)

参数调优是“最后手段”，优先解决 SQL 和架构问题。

### 1. 内存相关 (Memory)
*   **`innodb_buffer_pool_size`** (核心)：
    *   建议值：物理内存的 50% - 75%。
    *   作用：缓存数据和索引。太小导致频繁磁盘 I/O，太大导致系统 Swap。
*   **`innodb_log_buffer_size`**：
    *   建议值：8M - 32M。
    *   作用：Redo Log 缓冲区。大事务可适当调大。

### 2. 连接与线程 (Connection & Thread)
*   **`max_connections`**：
    *   建议值：1000 - 3000 (视业务而定)。
    *   注意：设置过大如果不配合连接池，会导致线程切换开销巨大。
*   **`thread_cache_size`**：
    *   建议值：`8 + (max_connections / 100)`。
    *   作用：缓存空闲线程，避免频繁创建销毁线程。

### 3. I/O 相关 (I/O)
*   **`innodb_flush_log_at_trx_commit`**：
    *   `1` (默认)：最安全，每次提交刷盘。
    *   `2`：高性能，每秒刷盘。适合允许丢失 1 秒数据的场景。
    *   `0`：性能极高，但不安全。
*   **`sync_binlog`**：
    *   `1` (默认)：每次提交刷 Binlog。保证双 1 (与上个参数配合) 数据不丢。
    *   `1000`：积累 1000 个事务刷一次，性能好。
*   **`innodb_io_capacity`**：
    *   根据磁盘 IOPS 设置。SSD 可设为 2000-5000，机械盘 200。

### 4. 操作系统层面
*   **Swap**：设置 `vm.swappiness = 0` (或 1)，尽量不使用 Swap。
*   **File Descriptors**：`ulimit -n 65535`。
*   **IO Scheduler**：SSD 建议使用 `noop` 或 `deadline`，机械盘使用 `cfq`。

## 四、实战案例总结

### 案例 1：分页查询优化
**问题 SQL**：
```sql
SELECT * FROM order LIMIT 1000000, 10;
```
**原因**：MySQL 需扫描 1000010 行，丢弃前 1000000 行。
**优化方案**：
```sql
-- 利用覆盖索引先查 ID，再回表
SELECT * FROM order t1 
JOIN (SELECT id FROM order LIMIT 1000000, 10) t2 
ON t1.id = t2.id;
```

### 案例 2：隐式转换杀手
**问题**：用户表 `phone` 字段有索引，但查询巨慢。
**SQL**：`SELECT * FROM user WHERE phone = 13812345678;`
**原因**：`phone` 是 varchar，输入是 int，MySQL 会对每行 `CAST(phone AS signed)`，导致全表扫描。
**优化**：`WHERE phone = '13812345678';`
